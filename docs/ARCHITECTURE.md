# ASTRA architecture

ASTRA is a modular monolith with one deliberately decoupled part: the simulation
engine. A single FastAPI process serves the API, the WebSocket stream and the
built React frontend, so the demo needs one command and one port.

```
 Browser (React + Three.js)                    FastAPI process
 ┌───────────────────────────┐   REST (JWT)   ┌──────────────────────────────────┐
 │ role dashboards           │ ─────────────▶ │ app/api      RBAC on every route │
 │ Test Operator console     │                │ app/services planner, assistant, │
 │ MissionView  ◀── frames ──│ ◀─ WebSocket ─ │              registry, runtime   │
 │  3D scene · charts · chat │   (read-only)  │        │ builds from a snapshot  │
 └───────────────────────────┘                │        ▼                         │
 Phone: /view/<token> (QR)                    │ astra_sim   deterministic engine │
                                              └────────────┬─────────────────────┘
                                                           ▼
                                           SQLite (default) or PostgreSQL
```

## Stack and why

| Layer | Choice | Reason |
|---|---|---|
| Backend | Python 3.11, FastAPI, SQLAlchemy 2, Pydantic 2 | Typed validation on every write path; native WebSockets |
| Database | SQLite by default, PostgreSQL via `ASTRA_DATABASE_URL` | Zero-setup offline demo; the same code and tests run on PostgreSQL 16 |
| Engine | `astra_sim`, pure Python, no framework or database imports | Reproducible, unit-testable, replaceable |
| Frontend | React 18, TypeScript, Vite, Three.js (no wrapper) | Direct control of the render loop for laptop performance |
| AI | `LLMProvider` protocol: local, Anthropic, OpenAI-compatible | Provider-agnostic, deterministic fallback always available |
| Charts, QR | Custom canvas charts; QR SVG generated by the backend | No runtime CDN or font dependency: the UI works fully offline |

## The four layers of the product

### 1. Physical sensor layer (`app/api/physical.py`)

- **Sensor registry** with relational core fields (range, datasheet accuracy,
  maximum plausible rate, resolution, observed ground-truth channel) plus
  **validated custom fields** defined in `custom_field_defs`.
- **Lifecycle** Draft → Active → Archived (archived can return to draft). Only
  active sensors are simulated. Activation requires a default simulation profile
  and all required custom fields.
- **Versioning**: every edit and status change stores a snapshot in
  `sensor_versions`.
- **Simulation profiles**: baseline, bias, noise, drift, random spikes, stuck
  values, disconnections. **Failure signatures** name fault patterns that the
  planner can inject per test.

### 2. Medical knowledge layer (`app/api/medical.py`)

Conditions with symptoms, sensor indicators, recommendations and scientific
sources; multi-sensor warning rules; dataset metadata imports (CSV/JSON: schema,
row count, checksum, five-row sample); synthetic astronaut profiles.

A rule is a list of clauses combined with ALL or ANY. Each clause compares an
aggregate of one sensor (`last`, `mean`, `min`, `max`, `slope_per_min`, `delta`
over a window) with a threshold. A rule must hold for `sustain_s` before it
raises and be false for `clear_after_s` before it clears.

### 3. Deterministic simulation engine (`backend/astra_sim/`)

```
plan.py      strict plan schema (unknown fields rejected, every number bounded)
timeline.py  compiles a plan into absolute times and positions; enforces the
             physical state machine (hatch → exit → walk → kneel → collect …)
physics.py   LAYER 1  ground truth: physiology, suit, environment
sensors.py   LAYER 2  sensor output: truth + profile noise/faults + injected faults
quality.py   LAYER 3a data quality: DataQualityAssessor + warning hysteresis
rules.py     LAYER 3b medical rules on trusted readings only
engine.py    one step() = layers 1 → 2 → 3a → 3b, returns a frame
world.py     real terrain height field, lander pose, waypoints
```

**Strict separation.** Layer 3 is handed layer 2 output only. The quality
assessor's inputs are `RawSample(t, value)` objects and datasheet metadata; a
test asserts it never receives ground truth. Sensor faults never change ground
truth (also tested).

**Determinism.** Every stochastic component draws from its own stream derived
from `sha256(seed:name)`, and each sensor draws a fixed number of variates per
tick. The same plan, seed and catalogue snapshot produce bit-identical frames, so
**Restart** replays a session exactly. This is tested at engine level and through
the WebSocket.

**Scientific constraint.** Radiation and thermal stress are independent. The
radiation multiplier only reaches `rad_dose_rate_usv_h` and `rad_dose_cum_usv`;
no physiological or thermal variable reads them. Tests compare runs with and
without a radiation event and require every thermal and vital-sign channel to be
identical.

**Data quality versus medical warnings.**

| | Data-quality warning | Medical warning |
|---|---|---|
| About | a sensor | the astronaut |
| Raised by | `DataQualityAssessor` flags: `DISCONNECTED`, `OUT_OF_RANGE`, `STUCK`, `SPIKE`, `EXCESS_NOISE`, `IMPLAUSIBLE_TREND` | a configured rule holding on trusted data |
| Effect on rules | readings marked bad or missing are excluded; the rule shows as **inhibited** | — |
| UI | violet, dashed card, "sensor problems, not medical findings" | amber/orange/red card with evidence and recommendations |

**ML trust-layer seam.** `DataQualityAssessor` is a protocol:

```python
def assess(self, sensor: SensorSpec, samples: Sequence[RawSample],
           context: Mapping[str, Sequence[RawSample]]) -> QualityAssessment
```

Any object with this method can be passed as `EngineConfig.assessor`. `context`
carries the recent raw windows of all sensors for cross-sensor models. The
default `RuleBasedQualityAssessor` cannot detect a pure calibration bias; that is
the intended first job for a learned assessor.

### 4. 3D Mars environment and ASTRA AI

- **Terrain** (`frontend/src/mission/MarsScene.ts`): a 512 m, 1 m/post patch of
  the HiRISE DTM centred on the landing site, stitched without cracks into a
  3 km, 16 m/post surround. The backend loads the same height field to compute
  walking grade, which feeds metabolic rate.
- **Scene**: procedural lander with hatch and ramp, articulated astronaut (idle,
  turn, walk, egress, kneel, collect, stand) blended toward the pose in each
  frame, route ribbon, travelled trail, waypoint beacons, sample ring.
- **Cameras**: third person, first person, overview, close-up. Orbit and zoom are
  local view state.
- **Performance**: one draw call per terrain mesh, instanced rocks, capped pixel
  ratio. If the first seconds are slow the scene drops shadows and resolution
  automatically; small screens start in that mode.
- **ASTRA AI** (`app/services/assistant.py`): the context is built from sensor
  output, data-quality state, warnings with evidence, scenario events, the plan
  and the medical knowledge base. It contains no ground truth, so the assistant
  cannot quote a value the dashboards do not show.

## Natural-language tests

```
prompt ──▶ LLM provider (if configured) ──▶ JSON ──┐
   │                                               ├─▶ SimulationPlan schema ─▶ compile_plan
   └─────▶ deterministic planner ─────────▶ JSON ──┘        (strict)            (world + sensors)
```

Both generators only produce JSON. Validation is the single gate: unknown
actions, unknown fields, out-of-range numbers, impossible sequences, unknown
waypoints or inactive sensors are rejected with readable messages. An invalid LLM
answer is discarded and the deterministic planner runs. Nothing in a plan can
name code, files or commands.

Actions: `OPEN_HATCH`, `ASTRONAUT_EXIT`, `WALK_TO_WAYPOINT`, `KNEEL`,
`COLLECT_SOIL_SAMPLE`, `STAND_UP`, `WAIT` (sequential activities) and
`THERMAL_LOAD_CHANGE`, `RADIATION_EXPOSURE_CHANGE`, `SENSOR_FAULT_INJECTION`
(overlay events triggered at a time or relative to an activity step).

## Sessions and the live stream

Creating a session freezes a **snapshot** of the catalogue (active sensors with
their default profiles, enabled rules, world, astronaut, medical knowledge) into
`sim_sessions.config_snapshot`. The engine is always built from that snapshot, so
later catalogue edits cannot change an existing session.

`app/services/runtime.py` holds one `LiveSession` per session: the engine, a ring
buffer of frames, the event list and the subscriber queues. An asyncio task steps
the engine at `speed ×` real time and broadcasts batches of frames. Database
writes (one frame per simulated second, events, warnings) are batched and run in
a worker thread.

**WebSocket** `/api/ws/sessions/{id}` is read-only. Inbound messages are ignored.
Server messages:

| `type` | Content |
|---|---|
| `hello` / `reset` | session state, columnar history (about 1 Hz), events, latest frame |
| `frames` | one or more frames: activity, astronaut pose, truth, sensors `[value, quality, flags]`, conditions, active warnings, rule monitor, new events |
| `state` | status, speed, run, simulated time |
| `notice` | critical messages such as an emergency stop |

Playback control is REST (`POST /api/sessions/{id}/control`) so it passes through
RBAC and the audit log.

## Roles and server-side RBAC

Every route declares its roles with `require_roles(...)`. The frontend's route
guards are a navigation convenience only.

| Capability | Admin | Physical | Medical | Operator | Viewer | QR token |
|---|---|---|---|---|---|---|
| Users, config, audit, emergency stop | ✔ | | | | | |
| Edit sensors, profiles, custom fields, signatures | | ✔ | | | | |
| Edit conditions, rules, sources, datasets, astronauts | | | ✔ | | | |
| Read both catalogues | ✔ | ✔ | ✔ | ✔ | | |
| Generate plans, create and control sessions | stop only | | | ✔ | | |
| Issue and revoke QR viewer tokens | ✔ | | | ✔ | | |
| Watch sessions, chat with ASTRA | ✔ | ✔ | ✔ | ✔ | ✔ | own session only |

**QR viewer tokens** are random 192-bit values shown once and stored as SHA-256
hashes. Each is bound to one session, expires, can be revoked, and is re-checked
every few seconds on an open stream.

**Other measures:** scrypt password hashing, login throttling, JWT bearer tokens
signed with a per-installation key, an append-only audit log for every
state-changing action, validated configuration keys, protection against removing
the last administrator, upload size and type limits.

## Database schema

26 tables in four groups (`app/models.py`):

- **platform**: `users`, `audit_logs`, `system_config`
- **physical**: `sensors`, `sensor_versions`, `custom_field_defs`,
  `simulation_profiles`, `failure_signatures`
- **medical**: `medical_conditions`, `symptoms`, `condition_symptoms`,
  `condition_indicators`, `condition_sources`, `warning_rules`,
  `recommendations`, `scientific_sources`, `datasets`, `astronaut_profiles`
- **mission**: `waypoints`, `scenarios`, `sim_sessions`, `session_events`,
  `telemetry_frames`, `warning_records`, `viewer_tokens`, `chat_messages`

## Engineering assumptions

- Simulation tick is 0.5 s; all sensors are sampled every tick.
- Physiology is a set of first-order models tuned to be plausible and legible in
  a five-minute demo, not validated against human data.
- The default thermal stress event (+600 W external load, cooling at 30%) is
  deliberately strong so a warning appears within the demo.
- Chat history is kept per author; QR viewers each have their own thread.
- At most four simulations run at once to protect a demo laptop.
